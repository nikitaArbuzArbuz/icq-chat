привет, делаю тестовое на java бэкенд, нужна помощь с проектом. спринг использовать не надо, поэтому используй javalin.

суть: чат по типу icq. пользователи логинятся, пишут друг другу личные сообщения в реальном времени и видят статусы доставки и прочтения. групповые чаты не нужны, только один на один. все сообщения хранятся в бд.

структура репозитория: в корне две папки, backend и frontend, у каждой свой dockerfile. в корне лежат docker-compose, общий readme и .env

по стеку давай так:
- java 21, сборка gradle, build.gradle.kts
- javalin 6 + websocket
- postgres, миграции liquibase, пусть запускаются автоматически при старте приложения, отдельный контейнер под него не нужен
- доступ к бд через чистый jdbc и hikari для пула соединений, без хибернейта и без orm вообще
- jwt для авторизации, пароли хешируем через bcrypt
- фронт на react и vite, без тяжёлых ui библиотек
- docker-compose поднимает postgres, бэк и фронт. фронт собирается и раздаётся через nginx, который проксирует запросы к апи и вебсокету на бэк

по функционалу:
- регистрация и логин, на выходе jwt, живёт сутки. секрет для подписи берётся из переменной окружения JWT_SECRET. id пользователя на сервере всегда берётся из токена, никогда не из того что прислал клиент в запросе или сообщении
- список пользователей с поиском по логину. у каждого показываем онлайн он или нет и сколько от него непрочитанных сообщений
- история переписки с конкретным пользователем через рест, с курсорной пагинацией, чтобы старые сообщения подгружались при скролле вверх, а не всё одним запросом. параметры давай before, это id сообщения, старше которого грузим, и limit. если before не передан, отдаём самые последние сообщения. limit по умолчанию 50, максимум 100, если пришло больше, обрезаем до 100. внутри страницы сообщения отсортированы от старых к новым, то есть сразу в том порядке, в котором их показывать. в ответе есть флаг, остались ли ещё более старые сообщения
- отправка сообщений идёт через websocket. клиент генерирует свой clientId для каждого сообщения, и если из-за проблем с сетью он отправит его повторно, дубля в базе быть не должно
- после сохранения сообщения в базу сервер отправляет отправителю подтверждение: clientId, серверный id и время создания. только после него фронт показывает первую серую галочку. если пришло повторное сообщение с тем же clientId, сервер не ругается ошибкой, а возвращает то же самое подтверждение с тем же серверным id
- статусы сообщения: SENT, DELIVERED, READ. DELIVERED ставится не когда сервер отправил сообщение в сокет, а когда клиент получателя прислал подтверждение что получил. отправитель получает обновления статусов в реальном времени
- прочтение идёт через сокет: когда получатель открыл переписку или в ней появилось новое сообщение, клиент шлёт id последнего прочитанного сообщения. сервер одним update в базе помечает как READ все входящие сообщения от этого собеседника с id меньше или равным этому, и уведомляет отправителя
- статус только растёт: SENT, потом DELIVERED, потом READ, назад никогда. запоздалое подтверждение доставки не должно откатить READ обратно в DELIVERED. прочтение без отдельной доставки тоже нормально, сразу READ. у получателя может быть несколько вкладок и подтверждения придут несколько раз, повторы ничего не должны ломать и не должны рассылать лишние уведомления отправителю. проще всего это делать условием в самом update, а не проверкой в коде перед ним
- если получатель офлайн, сообщение остаётся SENT. когда он подключается, сервер досылает ему все недоставленные, получает подтверждение и уведомляет отправителя
- websocket авторизуется по токену, токен передаём в query параметре при подключении. если токен невалидный или истёк, закрываем соединение
- у одного юзера может быть открыто несколько вкладок, онлайн он считается пока жива хотя бы одна. во все вкладки должно приходить:
  - входящие сообщения и обновления их статусов
  - свои отправленные сообщения: если отправил из одной вкладки, сообщение появляется и в остальных
  - прочтение: если прочитал переписку в одной вкладке, счётчик непрочитанных от этого собеседника обнуляется во всех
- при входе и выходе пользователя остальным рассылается обновление онлайн статуса
- пинг для зависших соединений, чтобы мёртвые сессии закрывались и юзер не висел онлайн вечно
- порядок сообщений определяется по id из базы, а не по времени клиента
- переписка с самим собой: в списке контактов она всегда первая и называется избранное. такие сообщения сразу сохраняются со статусом READ, без подтверждений доставки и прочтения, и в счётчик непрочитанных не попадают. онлайн статус для неё не показываем. сообщение сразу появляется во всех моих вкладках

валидация:
- логин от 3 до 32 символов, латиница, цифры и подчёркивание. пароль от 8 символов. если логин занят, отвечаем 409
- сообщение не может быть пустым или из одних пробелов, максимальная длина 4000 символов
- писать самому себе можно, это как избранное в телеграме. несуществующему пользователю писать нельзя
- ошибки в ресте отдаём json с понятным кодом и текстом. ошибки при отправке через сокет приходят типом error вместе с clientId, чтобы фронт понял, какое именно сообщение не ушло, и показал это у него

все сообщения в сокете в json с полем type, чтобы было понятно что это: новое сообщение, подтверждение сохранения отправителю, подтверждение доставки, прочтение, смена онлайн статуса, ошибка. опиши формат каждого, отдельно что шлёт клиент и что шлёт сервер.

по структуре бэка хочу нормальное разделение на слои: контроллеры, сервисы и репозитории. реестр активных сокет сессий отдельным компонентом, потокобезопасный. конфиг через переменные окружения с дефолтами, логирование через slf4j и logback. глобальный обработчик ошибок, чтобы отдавал json, а не стектрейс. индексы в бд под выборку истории переписки и подсчёт непрочитанных, уникальный индекс на отправителя и clientId.

фронт: слева список контактов с онлайн индикатором и счётчиком непрочитанных, справа окно переписки. у своих сообщений галочки статуса - одна серая отправлено, две серые доставлено, две синие прочитано. пока нет подтверждения сохранения от сервера, у сообщения значок ожидания вместо галочки. при потере соединения фронт сам переподключается и переотправляет сообщения, на которые не пришло подтверждение.

readme: как запустить локально, какие переменные окружения нужны, команды сборки и запуска для бэка и фронта отдельно, как поднять всё через docker-compose, примеры curl для всех рест эндпоинтов, формат сообщений в websocket и как проверить сокет через websocat. отдельно напиши как быстро проверить чат, открыть два браузера или обычное окно и инкогнито, залогиниться разными юзерами и переписываться. и добавь пару тестовых юзеров в миграции, чтобы сразу можно было зайти.
